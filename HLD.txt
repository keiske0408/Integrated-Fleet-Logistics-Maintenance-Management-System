# Executive Proposal: Hulma Integrated Fleet Logistics & Maintenance Management System

**Document Type:** High-Level Client System Proposal  
**Target System:** Hulma Full-Stack Vehicle Fleet Logistics & Maintenance Management Platform  
**Grounded Sources:** *Hulma Vehicle Fleet Logistics and Maintenance Management Sources (TSRF Specification & Fleet Chat Guidelines)*  

---

## 1. Executive Summary

The **Hulma Integrated Fleet Logistics & Maintenance Management System** is a unified, full-stack digital platform designed to modernize and centralize vehicle operations across the organization [1, 6]. Currently, fleet logistics rely on manual paper vouchers via Transportation Service Request Forms (TSRF) [1, 3] and informal group chat communications (e.g., the *"Hulma - Vehicle PMS & Repair (Fleet)"* channel) [6]. 

By consolidating dispatch requests, mileage tracking, maintenance validation, and procurement approvals into a single automated system, this platform eliminates vehicle downtime, enforces maintenance accountability, and creates strict financial controls for repair expenditures [6].

---

## 2. Problem Statement & Operational Objectives

### Current Challenges
* **Fragmented Communication:** Fleet updates, repair requests, and status tracking are scattered across group messaging chats [6].
* **Unmonitored Mileage & PMS:** Lack of centralized kilometer (KM) tracking leads to missed Preventative Maintenance Services (PMS), resulting in avoidable mechanical failures and costly repairs [6].
* **Uncontrolled Maintenance Spending:** Repair work is often initiated without prior validation of past maintenance records or formal procurement approval [6].
* **Manual Dispatch Overhead:** Processing Transportation Service Request Forms (TSRF) manually slows down project logistics and asset transfers [1, 3].

### Strategic System Objectives
1. **Centralize Fleet Visibility:** Maintain a real-time digital inventory of all team vehicles, current KM readings, and maintenance statuses [6].
2. **Automate Mileage-Based Maintenance:** Proactively trigger PMS alerts based on standard vehicle manufacturer intervals (e.g., every 5,000 km) [6].
3. **Enforce Approved PR Gating:** Establish approved Purchase Requisitions (PR) as the mandatory gate before any PMS or repair work order can proceed [6].
4. **Digitize Logistics & Dispatch:** Streamline the TSRF workflow from initial request to multi-department approval and driver manifest generation [2, 5].

|                                                                               |  |
|  [ Module B: Fleet Maintenance & Repair ] <-----------------------------------+  |

|  - Auto PMS Trigger (Every 5,000 KM)                                             |

|                                                                                  |
|  [ Module C: PR Gating & Procurement Engine ] <-------------------------------+  |
|  - Approved PR Gatekeeper (Mandatory Unlock)                                     |
|  - Procurement Order Sync & Fulfillment Status                                   |
|                                                                                  |

### Module A: Transportation Service Request (TSRF) & Logistics
* **Digital Request Portal:** Replaces manual forms with a structured digital intake specifying project names (e.g., *Asset Retrieval and KE Biometric Project*), request dates, expected call times, and cut-off enforcement (4:00 PM daily cut-off) [1, 3, 5].
* **Multi-Stop Route & Location Management:** Tracks origins, destinations, Google Map addresses, call-in/out times, and waiting times across corporate facilities (e.g., MMG Warehouse to Kingston Excell) [1, 3, 5].
* **Asset & Vehicle Allocation:** Supports flexible vehicle type selection—including Commuter Vans, 4W/6W/10W trucks, container units, and 3rd-party logistics providers (Lalamove, Transportify) [4, 5].
* **Manifest & Cargo Control:** Enforces mandatory recording of passenger names (e.g., IT support staff, field teams) and loaded products, materials, or equipment [2, 5].
* **Multi-Tier Authorization:** Automated routing for formal endorsements across IT Support, CITO, Finance Manager, and Logistics Head [2, 5].

### Module B: Vehicle Fleet & Kilometer Monitoring
* **Central Vehicle Registry:** Comprehensive dashboard listing every team vehicle, plate number, assigned driver, and current KM reading [5, 6].
* **Automated PMS Calculator:** Calculates usage against manufacturer schedules (e.g., 5,000 km intervals) and automatically flags vehicles approaching or due for PMS [6].
* **Maintenance & Repair Audit Rule:** Before endorsing a vehicle for repair, the system verifies whether required PMS was maintained. If PMS was skipped, the system forces submission of a mandatory **Incident Report** explaining the circumstances prior to proceeding [6].

### Module C: Approved PR Gatekeeper & Procurement Integration
* **Strict PR Approval Gate:** An **Approved Purchase Request (PR)** serves as the hard system gate. Repair or PMS work orders remain locked in "Pending PR Approval" status until Procurement inputs the approved PR reference [6].
* **Procurement Hand-off:** Automatically notifies Procurement upon PR approval, allowing immediate coordination and execution without delay or chat confusion [6].
* **Real-time Status Tracking:** Centralized view displaying Vehicle Details, Current KM, PMS Due Date/KM, Repair Status, PR Status, and Completion Updates [6].

## 4. End-to-End Operational Workflow

```
[ Step 1: Trip Dispatch (TSRF) ]
   └── User files digital TSRF -> Approvers sign off -> Driver executes trip -> Returning KM logged [1, 2, 5]

[ Step 2: Automated Mileage Check ]
   └── System updates vehicle KM -> Checks against 5,000 KM PMS threshold [6]

[ Step 3: Maintenance Request Trigger ]
   ├── If PMS Due -> Create PMS Order [6]
   └── If Repair Requested -> Check PMS History:
          ├── PMS Up-to-Date -> Create Repair Order [6]
          └── PMS Overdue -> Block Order -> Require Mandatory Incident Report [6]

[ Step 4: PR Gating & Procurement ]
   └── Work Order generated -> Pending PR Approval -> Approved PR Gate Unlocked -> Procurement Executes Work [6]
```

1. **Trip Execution & Odometry Update:** A driver completes a TSRF assignment (e.g., shuttle or pick-up transaction). Upon return, the ending odometer reading is recorded, automatically updating the vehicle's total accumulated mileage [1, 5, 6].
2. **Interval Evaluation:** The system evaluates current KM against the next scheduled PMS milestone [6].
3. **Maintenance Validation:**
   - If PMS is due, a PMS request is automatically drafted [6].
   - If a repair request is submitted, the system checks historical PMS compliance. If PMS was neglected, an Incident Report must be uploaded [6].
4. **PR Gatekeeper Enforcement:** The request is queued for financial review. Once the Purchase Requisition is approved, the system unlocks the work order and sends an alert to Procurement [6].
5. **Work Execution & Status Tracking:** Procurement coordinates servicing. Status transitions dynamically: `PR Approved` -> `In Maintenance` -> `Work Completed` -> `Vehicle Operational` [6].

## 5. System Roles & User Permissions

| Role | Core Responsibilities & System Permissions |
| :--- | :--- |
| **Requestor / Project Staff** | Submits TSRF requests, inputs origin/destination, cargo items, and passenger manifests [2, 5]. |
| **IT & Department Heads** | Endorses department TSRF submissions and approves project logistics [2, 5]. |
| **Logistics & Fleet Manager** | Allocates vehicles/drivers, tracks mileage (KM), oversees PMS schedules, and validates repair requests [5, 6]. |
| **Finance Manager** | Reviews financial vouchers, checks TSRF budget allocations, and authorizes Purchase Requests (PR) [2, 3, 6]. |
| **Procurement Team** | Receives approved PR notifications, coordinates with external service centers/suppliers, and updates repair fulfillment status [6]. |

---

## 6. Business Impact & Return on Investment (ROI)

* **Reduced Vehicle Downtime:** Preventive tracking prevents major mechanical breakdowns and keeps the fleet operational [6].
* **Strict Cost & Financial Control:** Eliminates unauthorized maintenance expenses through mandatory PR gating [6].
* **Operational Accountability:** Enforces policy compliance via mandatory Incident Reports for neglected vehicle maintenance [6].
* **Auditability & Traceability:** Replaces lost chat messages with a permanent digital audit trail of trips, approvals, mileage, and repair histories [1, 6].

## 7. Strategic Implementation Roadmap

This roadmap replaces the week-based proposal below as the active plan for the dynamic TSRF form, LOV, authentication, reporting, and rollout work. Implementation and reporting verification were refreshed on 2026-10-12; local tests and development-header browser checks do not establish production readiness. Existing capabilities are identified so implementation extends them rather than rebuilding them. Complete one phase at a time and verify its exit criteria before beginning the next phase.

### Verified Baseline

- **Implemented:** Generic LOV lists, attributes, items, API routes, frontend integration, and the four system lists. Legacy reference-data tables/routes remain in place.
- **Implemented:** Versioned form definitions, draft/publish flow, schema-driven TSRF renderer, field registry, declarative rules, server-side submission validation, workflow transitions/events, configurable 4:00 PM Asia/Manila cutoff, vehicle lookup, report projection with PII exclusion, and print view. The TSRF UI is list-first, offers an explicit New Request guide, returns to and selects successful submissions, shows event history and the linked approver or current role queue, and prints historical requests from their pinned schema with status metadata.
- **Implemented since the earlier status snapshot:** Returned-request edit/resubmit with owner and field-level checks; sanitized active-driver lookup; ending odometer integration on completion; builder/workflow Activity History; Entra and Fleet-local authentication, signup approval, password reset, and secure first-admin bootstrap.
- **Still open:** Validate printed TSRFs against the approved entity-specific paper samples; decide and implement dynamic server-backed role policies if administrators need to change permissions without a deployment; verify real Entra and SMTP integrations and production deployment controls. Fixed CASL policies remain authoritative until dynamic policy enforcement is implemented and tested.
- **LOV slices complete:** Legacy reference rows are copied after legacy seed inserts during startup; a fresh-database smoke check confirmed all four defaults (8 departments, 8 vehicle types, 7 maintenance categories, 3 vendors). LOV item writes validate declared attribute keys/types/required/select options, hierarchy parent/list/cycle rules, and effective-date ordering. Active lookups and both dynamic/legacy TSRF submission validation enforce effective windows using server time.
- **Implemented security baseline:** Role catalog GET routes remain available; writes are admin-gated and return 409 until dynamic policies are wired, and the Roles UI is read-only. Non-reviewer access to reports, details, events, and data edits is scoped to the creator; detail responses omit explicitly hidden fields and raw JSON storage columns. Published field keys cannot be renamed or removed on later versions, while labels remain editable. Legacy reference-data writes require the admin LOV permission. Production API writes fail closed when Arcjet is missing or errors; test mode bypasses external Arcjet and auth keeps its in-process limiter. Backend regression tests cover these boundaries.
- **Implemented API contracts:** Existing LOV, form, and role-read routes are registered in `src/api/openapi.ts`; `openapi.json` and `src/api/generated-types.ts` were regenerated from that source.

### Delivery Phases

1. **Phase 1: Security and API Contract Foundations — Implemented; staging verification pending**
   - Keep fixed CASL policies as the authoritative server permission source. Dynamic role catalog writes and UI editing are disabled until the role catalog can safely drive backend policy evaluation.
   - Enforce owner-scoped submission reads, reports, events, and edits while preserving reviewer access. Filter detail data and label snapshots according to the pinned version's current-stage field visibility.
   - Published field-key immutability is implemented in the publish API and builder UI. LOV, form lifecycle, and role-read paths are registered in the generated API contract.
   - Apply the global API write limit plus stricter form/TSRF/procurement policies. Production fails closed with 503 when required Arcjet protection is unavailable or errors; development/test behavior is documented.
   - **Implementation checks:** backend tests/build pass; non-admin role mutations are denied and admin catalog writes remain explicitly disabled; cross-owner submission access is denied; hidden fields are absent from details; published keys cannot change; generated paths/types are current.
   - **Release gate:** production Arcjet is configured and protected writes are verified in staging.

2. **Phase 2: LOV Completion and Backward-Compatible Migration — Complete (2026-10-07)**
   - Generic LOV items are canonical for Departments, Vehicle Types, Maintenance Categories, and Vendors. Startup backfill runs after legacy seeds, copies active/inactive state, is idempotent, and preserves existing LOV edits when legacy rows are stale.
   - Legacy reference-data URLs and response field names remain available as adapters over LOV. Legacy deletes deactivate items instead of removing referenced catalog data; inactive items are excluded from new active lookups and submissions.
   - The admin Reference Data Hub exports stable attribute-key CSV files and imports validated CSV batches. Imports upsert by code in one transaction, reject invalid or duplicate rows without partial writes, and preserve optional attributes omitted from an update.
   - Historical form submissions continue displaying their saved LOV label snapshots after an item is deactivated. Legacy tables remain in place; no destructive migration was performed.
   - **Verified exit checks:** backend integration tests cover backfill repeatability and precedence, legacy/generic parity, authorization, atomic import/upsert, deactivation, and historical snapshots; frontend CSV tests cover round-trip, legacy export compatibility, quoting, and validation errors. Backend and frontend builds pass.

3. **Phase 3: Form Schema, Runtime, and Builder UX — Complete (2026-10-07)**
   - The builder supports schema validation, field configuration (including select options and repeater row fields/limits), keyboard-accessible reorder, role/stage preview using runtime access defaults, and JSON import/export. Imports are validated and restricted to the current form key.
   - Drafts autosave after edits, editor history supports undo/redo, draft changes can be compared with the latest published version, and version/preview subroutes preserve direct links without changing the existing builder entry point.
   - Existing submissions remain pinned to their original form version; the current seeded GVE/HULMA definition and intake route remain available during rollout.
   - **Verified exit checks:** frontend tests cover field configuration validation, reorder, role/stage projection, JSON import validation, schema version differences, and undo/redo; frontend build passes.

4. **Phase 4: Rules, Workflow, Permissions, and Approvals — Complete (2026-10-07)**
   - Complete the configurable workflow: Draft → Submitted → Endorsement → Finance Verification when applicable → Approval → Dispatch Assignment → Confirmed → In Progress → Completed, with Returned, Rejected, and Cancelled paths and a Returned → edit → resubmit loop.
   - Default owner cancellation is now available from Submitted and Returned, with a required reason. The API permits it only for the request owner when the pinned workflow explicitly allows the requestor role; other-owner reads remain hidden. Late dynamic submissions are flagged and routed to their configured exception stage.
   - **Verified slices:** API tests cover owner-only cancellation, required cancellation reasons, and late exception-stage routing/event records.
   - **Verified exit checks:** workflow authorization, required reasons, returned edit/resubmit, department-head assignment, field projection, hidden-field tamper rejection at submission, and configured cutoff routing are covered by tests; frontend/backend builds pass.
   - Resolve approvers by role with department-head resolution from the Departments LOV. Rejection and cancellation require a reason. After the configurable 4:00 PM Asia/Manila cutoff, flag the request and require the configured exception approval.
   - Enforce field edit/read/hidden permissions on both UI and API. Add approval stamps and focused transition/denial tests.
   - **Exit checks:** tampered payloads and unauthorized transitions are rejected server-side; workflow edits require no code deployment.

5. **Phase 5: Fleet Integrations, Repeaters, Reporting, and Print — Implemented; paper-form acceptance pending**
   - Conditional Fleet Asset/3rd Party Trucking fields, normalized driver lookup, route/passenger/material repeaters, reportable-field exposure, print approval stamps/signature lines, and an ENTITIES LOV-driven GVE/HULMA letterhead are present. Dynamic TSRF completion now records ending odometer readings to the assigned vehicle using the existing monotonic/PMS rules; requestors cannot inject the ending reading at intake.
   - Builder changes have scoped Activity History records; successful LOV/workflow mutations are audit-logged with actor/path metadata only. Workflow audit labels distinguish returned, rejected, cancelled, completed, resubmitted, and approved transitions without storing request bodies or comments.
   - Remaining work: compare the generated print view to the approved GVE and HULMA paper samples, including field order, conditional fields, approval stamps, signatures, and page breaks. Keep passenger names, mobile numbers, and signatures classified as PII and out of unauthorized exports/logs.
   - **Implementation checks:** representative TSRF requests pass end-to-end API/UI tests; reports exclude PII; vehicle mileage updates follow existing validation rules.
   - **Acceptance gate:** fleet/business owners approve print parity for both entities.

6. **Phase 6: Submission Reporting and Audit Evidence — Implemented (2026-10-12); operational acceptance pending**
   - Reports now provides a server-backed submission register and restricted persistent audit history. Submission rows include reference, pinned form version, submission date, status/stage, cutoff flag, current responsibility, and safe reportable fields with historical lookup labels.
   - Server-side filters, pagination, and complete matching counts replace capped-list analytics. Counts and rows use one repeatable-read database snapshot. Calendar date filters use Asia/Manila; exported timestamps use UTC ISO format.
   - Administrators and administrator-assigned read-only auditors can access organization audit history. Other submission readers retain existing organization/owner scope. Auditors cannot approve, edit forms, or read raw submission details; public signup cannot request the auditor role.

The full frontend typecheck had 16 baseline diagnostics and 17 at final verification, all outside the reporting feature; unrelated working-tree changes were preserved.

7. **Phase 7: Production Readiness and Controlled Rollout — Not verified**
   - Configure the production database, HTTPS origins/CORS, session secret, Entra app registrations and role map, SMTP delivery, and Arcjet. Keep development identity headers and demo accounts disabled.
   - Run the secure one-time first-admin bootstrap; verify admin sign-in and account recovery without exposing bootstrap credentials or reset tokens.
   - Exercise signup/approval, local and Entra login, logout/CSRF, password reset, role denial, owner scoping, audit logging, and protected write limits in staging. Verify database migration, backup/restore, and operational alert/retention procedures before live use.

8. **Phase 8: Dynamic Server-Backed Role Policies — Deferred; decision required**
   - Confirm whether role and permission changes must be configurable by administrators at runtime. Until approved, retain fixed CASL authorization and the read-only role catalog; catalog edits must not imply access grants.
   - If approved, define the supported permission vocabulary and role-to-policy mapping, migrate/seed mappings, make policy evaluation server-authoritative, and add deny-by-default tests for every protected API family before enabling role writes in the UI.
   - **Exit checks:** API authorization uses persisted policy mappings; unsupported permissions and privilege escalation are rejected; policy changes are audited; tests prove both grants and denials; generated OpenAPI/types are current.

### Recommended Next Steps

1. **Close paper-form parity first.** Obtain the approved GVE and HULMA samples, create a field-by-field/signature checklist, adjust the versioned definition and print layout, then get fleet/business sign-off. This is the remaining user-facing acceptance item in the current TSRF delivery.
2. **Accept reporting and audit operations.** Review Phase 6 using representative submissions, verify KPI/filter/export results, assign auditors through administrator-managed accounts, and approve retention and access-review policy. Maintenance/procurement analytics and legacy TSRF aggregation remain separate follow-up scope.
3. **Run production-readiness work in parallel with paper review.** Provision staging integrations and secrets, bootstrap the first administrator securely, and verify Entra, SMTP, Arcjet, CSRF, backups, and audit operations. Do not enable live use until Phase 7 exit checks pass.
4. **Make the RBAC decision before building it.** If runtime permission administration is not a business requirement, keep fixed CASL and close the phase as intentionally deferred. If it is required, implement Phase 8 as a server-side authorization change; do not treat the UI role matrix or catalog as enforcement.
5. **Complete end-to-end UAT and controlled rollout.** Test requestor, department approver, finance, fleet, procurement, auditor, and administrator paths using representative trip/maintenance scenarios; record defects and acceptance, then roll out with monitoring and a rollback plan.

**Immediate implementation order:** paper sample/parity review → staging integration and security verification → role-policy decision → UAT and controlled rollout. Production configuration and security verification are release blockers, even if they proceed alongside print work.

### Approved Decisions

- Use one versioned TSRF definition for GVE and HULMA, with entity as an LOV-driven field.
- Keep existing `tsrf_requests` records and table; use `form_submissions` for the dynamic workflow.
- Resolve approvers by role, with department-head resolution from department LOV data.
- Use the supplied workflow order and the 4:00 PM Asia/Manila late-flag plus exception-approval policy.
- Add `react-router-dom` for builder subroutes and deep links.
- Reportable defaults: status, department, vehicle type, needed/completed dates, late flag, and entity. PII defaults: passenger names, driver mobile, contact phone, and signatures.
